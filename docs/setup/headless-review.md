# The headless review

P-HR (owner, 2026-11-16; `docs/specs/phase-1-see.md` → P-HR). After the author pushes and CI is green, the author session starts `/review-pr` itself as a separate headless `claude -p` process, through the installed wrapper `~/.config/moonshine/bin/review <pr> standard|deep` (`scripts/guard/review.mjs`). The review posts through `gh-post review`, as one started by hand does. This page records what the probes showed, what the wrapper checks, and what stays open. Probe results are counts and structure only (CLAUDE.md rule 5): the repository's own skills and agents by name, account-level ones as counts, nothing pasted from a log.

## What the wrapper does

In order; any refusal exits 1 and starts nothing. Nothing ran and nothing was posted, so the author may fix what the message names and run the wrapper again, except the two refusals that end "only the owner can clear this; ask the owner": a record of a run on this head that started and posted no review (step 6), and a missing decisions file (step 3) (PR #67 round 1); exits 5, 6 and 7 come after the start and are never retried: the author tells the owner (owner, 2026-11-17, PR #63 round 1).

1. Refuses inside a headless run (`MOONSHINE_HEADLESS` set, even empty), in `bin/review` before the environment is cleared and again in `review.mjs`; arguments are `<pr> standard|deep`.
2. The repository (`scripts/guard/github.mjs`, shared with `gh-post merge`): the git folder must be the one the guard was installed for (`mainGitDir` in `config.json`, so a `.git` file or `commondir` pointing elsewhere refuses), not shallow, no grafts, no replace refs; git runs with fsmonitor and hooks off.
3. GitHub, every read fatal: the PR open, not a draft, into `main`, from this repository (no fork, no `fork/` branch); CI as `gh-post merge` requires it; no review on the PR by another account with a marker, in any spelling: the body is read folded (NFKC, no zero-width characters or soft hyphens, lower case) and with every hyphen-like character as `-` and the small and full-width `<` and `>` as themselves (PR #67 round 1; `/review-pr` reads the round and round 2's diff from the markers of all reviews; P-AM2); no review of this head yet; round 1, or round 2 after a round 1 with a High, or with an owner finding on a PR whose body has the one line `Class: plain` (P-AM2, owner 2026-11-17); round 3 is the owner's, started by hand. Round 2 also needs round 1's head to be an ancestor of this head, and after owner findings an answer by the account, later than round 1, with the owner decisions block (CLAUDE.md → "Pull requests"), and the decisions file `Claude outputs/next/pr<n>-round1.md` in the checkout as a regular file, never read: each part of the path, from the checkout's real folder down, listed under that exact name (no other case) and no link (PR #67 round 1).
4. `main` is an ancestor of the head, and the PR changes no `CLAUDE.md`, `CLAUDE.local.md`, `.claude/` or `.mcp.json` at any depth (tree to tree, no rename detection, case-folded): such a PR is reviewed by hand.
5. The checkout is exactly the head: HEAD, no change, no untracked file, no submodule, no index flag, and no ignored instruction file at any depth, ignored folders included (beyond the local settings file, `settings.local.json` next to `settings.json`, the `.cc-writes` folder Claude Code keeps beside it, and `.DS_Store`); git lists an ignored nested repository, such as a package checkout in the adapters' build folder, as one folder, so the wrapper walks it, following no link, and allows there only the `.cc-writes` write log inside a `.claude` folder (PR #63 round 1); `git fsck` on the head and `main`.
6. The lock (below) and a session id; then, under the lock, no record of a run on this head that started and posted no review (step 12), so a run that stopped while this call waited counts (PR #67 round 1).
7. A private folder `~/Library/Caches/moonshine-review/run-*` with this run's settings (the denies of the run, `Write` and `Edit` on this run's scratchpad only, auto memory off; hooks kept), its MCP config (Context7 only) and the logs.
8. `claude` by the link the installer found, under `/usr/bin/caffeinate -i` where that exists (macOS; P-AM2, owner 2026-11-20), in an environment built from scratch: `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `LANG`, the wrapper's `PATH`, `MOONSHINE_HEADLESS=1`, `MOONSHINE_HEADLESS_PR`, `ENABLE_CLAUDEAI_MCP_SERVERS=false`, `GIT_NO_REPLACE_OBJECTS=1` and `core.fsmonitor=false`; flags `--session-id`, `--tools Read Write Edit Bash Task`, `--permission-mode default --permission-prompts none`, `--settings`, `--strict-mcp-config --mcp-config`, `--disallowedTools` the wrapper, `--no-session-persistence`, `--max-budget-usd 15|40`, `--output-format stream-json --verbose`. `--bare` (it needs an API key) and `--safe-mode` (it drops the read-boundary hook) are not used. The build number goes to the output.
9. The start gates, on **every** start event (one per turn of the main agent), exit 7: the session id is the wrapper's; `apiKeySource` is `none`; Context7 is the only MCP server; the tools are only `Task`, `Bash`, `Edit`, `Read`, `Write` and Context7's two (probe 4), so a tool a later build adds stops the run (a missing one does not); every plugin's `source` is a line of the owner's `~/.config/moonshine/review-plugins.txt`; and a start event within the first 20 lines and 120 seconds.
10. Limits: 60 minutes for `standard`, 120 for `deep` (exit 5); SIGTERM, SIGINT and SIGHUP end the run (exit 6). The child's process tree (its descendants and their process groups, walked until no new process appears) gets TERM, 10 seconds, then KILL.
11. On every exit, this run's review worktrees (`scratchpad/review/pr-<n>` and `pr-<n>-*` in its session folder, as `git worktree list` shows them) are removed by path; `git worktree prune` never runs.
12. Exit 0 only when `claude` exited 0, the last result event is `success`, `posts.jsonl` records exactly one review from this run's session, GitHub shows it as a review by the signed-in account, on this head, with a counted marker naming this head, dated no earlier than five minutes before the start (GitHub's clock and this machine's may differ), and the checkout is still exactly the head. Otherwise exit 6, never retried. Once `claude` has started, the wrapper writes `~/.config/moonshine/state/stopped-<n>-<head>.json` (the PR, the head, the exit, null while the run lasts, and the time; not named `review-*`, so never taken for a lock); exit 0 removes it, and exit 5, 6 or 7 adds its exit (PR #67 round 1). So a failure before the spawn records nothing, and a wrapper killed before it ends (SIGKILL, a crash) still leaves the record. Under the lock, step 6 refuses that head until the owner runs `~/.config/moonshine/bin/review-allow-retry <n>` from the owner's own terminal, which removes the PR's records; another head of the PR is not refused (P-AM2, owner 2026-11-20). When the record cannot be written at the start, the run stops with exit 6, and the output says so. A stopped run's reason names a sleep longer than a minute: every ten seconds the wrapper adds up how far the wall clock stepped beyond the monotonic one, which on macOS does not advance while the Mac sleeps. That has not been seen on a live sleep yet. The logs are written before the exit (at most two seconds). The run folder is removed on exit 0; on any other exit it is kept, the newest three only. The output names the exit, the reason and the folder, never review text.

**Keeping the Mac awake** (P-AM2, owner 2026-11-20; probe, 2026-11-21). `caffeinate -i <utility>` runs the utility in the process the wrapper started, so the lock's child is `claude` itself and the stale-lock rule above is unchanged; a forked `caffeinate` holds the `PreventUserIdleSystemSleep` assertion on the utility's behalf (`pmset -g assertions`) and keeps its exit status. Idle sleep cannot cut a run; a closed lid still does, so the owner's Mac stays open while a run is going (CLAUDE.md → "Pull requests").

`@builtin` plugins cannot be switched off through `enabledPlugins` in the run's settings (probe 4), so they are allowed by name in the owner's local file, outside the repository; the installer never creates, changes or removes it. A missing or empty file means that no plugin is expected.

## The lock

`~/.config/moonshine/state/review-<16 hex of the checkout path's sha256>.json` (`scripts/guard/review-lock.mjs`): the PR, the head, the session id, the checkout and its session folder, the wrapper's and the child's pid with their start times (`ps -o lstart=` in the C locale and UTC); when `ps` cannot read a start time, the wrapper refuses, and a lock without one counts as live. It is created exclusively; a lock whose wrapper and child are gone, or alive with another start time, is stale. A stale lock is acted on only when it names this checkout and a session folder under this checkout's scratch root; otherwise the wrapper refuses and names the file. Then a recorded child still alive is killed only when `ps` shows it started as the installed `claude` (else the wrapper refuses), that session's review worktrees of its PR are removed, and the file read is set aside by rename: when the renamed file is not the one read (another wrapper took the lock meanwhile), it is put back and the wrapper refuses (PR #63 round 1). A lock that cannot be read counts as live in `gh-post` and the hook, and refuses the wrapper, naming the file for the owner to remove.

While a live lock covers a checkout (its own, or a review worktree inside its session folder):

- `gh-post` sends only `review <the lock's PR>` with `event` `COMMENT` and `commit_id` the lock's head, from a file in the lock's session scratchpad, while that checkout is still exactly the head, and only once per session; everything else is refused, whatever the environment says;
- the pre-push hook refuses every push.

Under `MOONSHINE_HEADLESS` with no live lock, both refuse everything. The variable is the second layer, not the first: one variable of probe 1b never arrived.

**What a forged lock allows.** A sandboxed session cannot write the state folder (its writes are limited to the checkout, its scratchpad and `$TMPDIR`; `~` is read-denied), so it can neither forge, move nor remove the lock. Unsandboxed test code, which a review runs through `swift test` or `xcbuild test`, can write both the state folder and `~/Library/Caches/` (`scripts/guard/merge.mjs`; CLAUDE.md § Git), so moving the lock would close nothing. A forged live lock narrows `gh-post`: one `COMMENT` review on the PR and head it names, which `gh-post review` already sends today. A forged stale lock can make the next review do no more than a real stale one: kill a process `ps` shows started as the installed `claude` (with the start time the lock records), and remove review worktrees `scratchpad/review/pr-<n>*` of a session in this checkout's scratch root; a lock naming anything else is refused (owner, 2026-11-17, PR #63 round 1). The code that can forge it could do both itself. The lock stays in `state/` (owner's addition 4, 2026-11-16).

## What stays open

- The run's objects can change between the wrapper's checks and the reviewers' reads; accepted.
- An index entry's stat data can be forged so that `git status` reports a changed file as clean; accepted.
- A session set on it can write the state file through test code that runs outside the sandbox (`scripts/guard/merge.mjs`).
- A process that left both the child's tree and its process groups (re-parented after its parent exited, in a session of its own) survives the kill.
- The stream shows no hook events: whether an allowed plugin's hook ran cannot be seen.
- A review marker posted by another account after the wrapper's start check, and before `/review-pr` reads the reviews, can narrow round 2's `git diff <previous head>..HEAD`. `gh-post merge` refuses a PR when such a marker precedes its last round, after any round (P-AM2; PR #67 round 1, owner 2026-11-21).
- A stopped-run record can be removed by unsandboxed test code, as the state file can; `review-allow-retry`'s deny is the second layer (`.claude/settings.local.example.json`).
- The owner decisions file is checked for existence only: a session set on it could write it through unsandboxed test code, as it can the state file. The settings deny the Edit and Write tools and the sandbox's writes there (`.claude/settings.local.example.json`).
- `ps` is denied inside a session's sandbox: there the lock tests that read start times and process trees are skipped, and they run in CI. The installed tools run outside the sandbox.
